════════ CONTEXTO DEL PROYECTO ════════

LogiFleet es un sistema de gestión logística de flota. Importa ventas y
traslados internos desde Odoo, planifica despachos (vehículo + chofer + ruta),
calcula costos, y tiene una app móvil Expo para choferes.

Monorepo pnpm workspaces, Node 24, TypeScript 5.9. Estructura:

  lib/db/               Drizzle: schema (fuente de verdad) + migraciones embebidas
  lib/api-spec/         openapi.yaml — contrato de la API + config de Orval
  lib/api-zod/          GENERADO desde el spec — NO editar
  lib/api-client-react/ GENERADO desde el spec (hooks React Query) — NO editar
  artifacts/api-server/ API Express 5 (routers en src/routes/, servicios en src/services/)
  artifacts/logistics/  Web React + Vite + wouter + shadcn/ui
  artifacts/chofer/     App móvil Expo
  e2e/                  Vitest (API) + Playwright (UI)

Lee `replit.md` en la raíz y `.agents/memory/`. Para esta tarea son relevantes:

════════ POR QUÉ ESTA TAREA ════════

Odoo pasa un traslado de `Listo` a `Hecho` cuando el almacén de destino valida
la recepción. Durante todo el viaje el inventario dice que la mercancía sigue
en el origen. LogiFleet ya cubre ese hueco con `estadoLogistico`, pero le falta
el registro de lo que efectivamente pasó al llegar.

Hoy `dispatches` NO guarda ninguna hora real: solo `fechaEstimadaSalida` y
`fechaEstimadaLlegada`. Cuando el chofer marca "entregado" desde el celular no
se registra CUÁNDO llegó. El acta de llegada es el único lugar donde ese dato
existiría.

El acta tiene DOS MITADES, escritas por personas distintas en momentos
distintos:
  - mitad del chofer: hora real de llegada + novedades del viaje
  - mitad del almacén: quién recibió + novedades de la mercancía

════════ TRAMPAS — LEE ESTO ANTES DE ESCRIBIR CÓDIGO ════════

TRAMPA 1 — El GROUP BY de selectTraslados.
`selectTraslados` en `services/trasladoQueries.ts` calcula
`cantidadLineas: count(deliveryItemsTable.id)` con un `.groupBy(...)`.
Si agregas un `.leftJoin()` hacia `dispatches` o hacia la tabla nueva de actas,
un traslado con DOS despachos va a duplicar sus filas de `delivery_items` y
`cantidadLineas` va a salir al doble. Es un bug silencioso: nadie mira el
número hasta que un usuario reclama.
→ El campo nuevo se calcula con una SUBCONSULTA CORRELACIONADA `EXISTS (...)`
  dentro del `.select({...})`, NO con un join. No toques el groupBy.

TRAMPA 2 — Un traslado puede tener varios despachos.
El acta cuelga de `despachoId`, y un traslado puede tener un despacho cancelado
más uno activo. Toda consulta que vaya de traslado hacia acta debe filtrar
`dispatches.estado <> 'cancelado'`, si no vas a leer el acta de un viaje que se
canceló.

TRAMPA 3 — `fechaLlegada` NO es `createdAt`.
El chofer llega a las 3 y registra a las 5 porque no tenía señal. `createdAt`
dice cuándo se tecleó; `fechaLlegada` dice cuándo llegó el camión. Son dos
columnas distintas y ninguna se deriva de la otra. No pongas
`DEFAULT now()` en `fechaLlegada`.

TRAMPA 4 — Las novedades son null, nunca "".
Si el usuario no escribe nada, se guarda NULL. Nunca "" ni "ninguna" ni "N/A".
Es la regla 5 del repo aplicada a texto.

1. SCHEMA — `lib/db/src/schema/actas_llegada.ts`, tabla `actas_llegada`:

     id                 serial PK
     despachoId         integer NOT NULL UNIQUE REFERENCES dispatches(id) ON DELETE CASCADE
     -- mitad del chofer
     fechaLlegada       timestamptz NOT NULL
     registradaPorId    integer REFERENCES personnel(id)
     novedadesViaje     text
     -- mitad del almacén
     recibidoPor        text
     confirmadaPorId    integer REFERENCES personnel(id)
     confirmadaAt       timestamptz
     novedadesRecepcion text
     createdAt          timestamptz NOT NULL DEFAULT now()

   Exportarla desde `lib/db/src/schema/index.ts`.

   `despachoId` UNIQUE es deliberado: UN acta por despacho. Si hay que
   corregirla se edita, no se crea otra — así nadie tiene que preguntarse cuál
   de tres actas es la buena.

   `recibidoPor` es texto libre Y ADEMÁS existe `confirmadaPorId`: quien recibe
   físicamente el camión (un obrero del galpón) casi nunca es el mismo que
   teclea la confirmación en el sistema, y puede no tener cuenta. El texto
   captura el hecho; el FK captura la responsabilidad.

3. REFACTOR — sacar la resolución de identidad a un servicio compartido.

   Hoy la lógica Clerk → email → `personnel` vive como función local
   `resolveDriver(req, res)` dentro de `routes/driver.ts`, escrita solo para
   choferes (hasta el mensaje de error dice "No hay un chofer registrado...").
   La mitad del almacén se confirma desde la web, así que necesita lo mismo en
   otro contexto. Duplicarla es exactamente el error que ya cometimos una vez
   con la sincronización de estados.

   Crear `artifacts/api-server/src/services/currentPerson.ts`:

     export type CurrentPersonResult =
       | { ok: true; person: Personnel }
       | { ok: false; reason: "unauthorized" | "no_email" | "not_linked"; email?: string };

     export async function resolveCurrentPerson(req): Promise<CurrentPersonResult>

   OJO: la función NUEVA no escribe en `res` — devuelve un resultado y el
   llamador decide la respuesta HTTP. Eso es lo que la hace reusable.

   Después, `driver.ts` consume `resolveCurrentPerson` y mapea el resultado a
   las MISMAS respuestas que da hoy, **con los mensajes idénticos palabra por
   palabra** (`"no_email"` → 404 "Tu cuenta no tiene un email asociado.";
   `"not_linked"` → 404 "No hay un chofer registrado con el email X. Pide al
   administrador que agregue tu email en Personal."). La app del chofer muestra
   esos textos al usuario: si los cambias, cambias su UX sin querer.

   Este paso NO debe cambiar ninguna conducta observable. Es refactor puro.
