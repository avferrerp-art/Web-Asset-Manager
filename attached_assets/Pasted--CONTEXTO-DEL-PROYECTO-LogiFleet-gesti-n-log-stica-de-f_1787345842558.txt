════════ PARTE A — TRES GUARDS DE BACKEND ════════

Salieron de revisar la tarea anterior. Son chicos; van primero.

A1. RECHAZAR FECHAS DE LLEGADA EN EL FUTURO.

    Hoy no hay tope superior. Un celular con el reloj mal configurado (cosa
    común en Android barato) registra una llegada en 2099. Y como la alerta de
    recepción pregunta `fecha_llegada < now() - 24h`, ese traslado NUNCA va a
    aparecer como "recepción sin validar".

    Es el peor tipo de bug: falla en silencio y justo en la dirección
    peligrosa — el caso que la alerta existe para atrapar es exactamente el
    que se pierde.

    En `services/actasLlegada.ts`, exportar
    `TOLERANCIA_RELOJ_MINUTOS = 10` y rechazar `fechaLlegada` mayor a
    `now() + TOLERANCIA_RELOJ_MINUTOS`. La tolerancia existe porque el reloj
    del celular puede ir unos minutos adelantado sin que nadie tenga la culpa.

    Respuesta: 400 `{ error: "fecha_llegada_futura" }`, tanto en
    `POST /dispatches/{id}/acta` como en el endpoint del chofer.

A2. RECHAZAR ACTAS SOBRE DESPACHOS QUE NO SALIERON.

    Hoy se puede registrar una llegada sobre un despacho en `pre-despacho`
    (que nunca salió del almacén) o sobre uno `cancelado`. No corrompe nada
    —las lecturas ya filtran los cancelados— pero es un dato sin sentido que
    el sistema deja crear.

    En `POST /dispatches/{id}/acta`: si el despacho no está en `en-ruta` ni en
    `entregado` → 409 `{ error: "despacho_sin_salir" }`.

    NO agregues este guard dentro de `registrarLlegada()`: el endpoint del
    chofer la llama justo después de mover el despacho a `entregado`, así que
    ahí la condición siempre se cumple. El guard va en el router.

A3. `confirmadaAt` SE SELLA UNA SOLA VEZ.

    Hoy un `PATCH` para corregir un typo en `recibidoPor` reescribe la hora de
    confirmación. En `confirmarRecepcion()`, `confirmadaAt` y `confirmadaPorId`
    solo se escriben si `confirmadaAt` está en null. Una corrección posterior
    actualiza los textos pero no mueve la firma original.

════════ PARTE B — CONTRATO: FALTA EL DESPACHO EN TrasladoDetail ════════

Para registrar o confirmar un acta desde la web hace falta el `despachoId`, y
`TrasladoDetail` no lo expone. Si el traslado todavía no tiene acta, la web no
tiene forma de saber sobre qué despacho actuar.

En `openapi.yaml`, agregar a `TrasladoDetail`:

    despachoActivo:
      oneOf:
        - type: object
          required: [id, estado]
          properties:
            id: { type: integer }
            estado: { type: string }
        - type: "null"

Es el MISMO despacho no cancelado que `getTraslado` ya resuelve para poblar
`acta` — reusa esa consulta, no escribas una segunda con otro criterio. Dos
reglas distintas para "cuál es el despacho del traslado" es como se empiezan
a contradecir las pantallas.

Después: `pnpm --filter @workspace/api-spec run codegen`.

════════ PARTE D — WEB: TARJETA DEL ACTA ════════

Archivo: `artifacts/logistics/src/components/traslado-detail-sheet.tsx`.

D1. Tarjeta nueva "Acta de llegada", en el cuerpo con scroll, ARRIBA de
    "Líneas del Traslado". Tres estados:

    (a) `despachoActivo === null` → no se muestra la tarjeta. Un traslado sin
        despacho no tiene llegada que registrar.

    (b) `acta === null` → "Sin acta de llegada" y, solo si
        `despachoActivo.estado` es `en-ruta` o `entregado`, un botón
        "Registrar llegada" que abre el formulario de la mitad del chofer
        (fecha/hora + novedades del viaje) y hace `POST`.
        Si el despacho está en `pre-despacho` o `aprobado`, texto explicativo
        y sin botón — el guard A2 lo rechazaría igual, pero un botón que
        siempre falla es peor que no tenerlo.

    (c) `acta !== null` → mostrar la mitad del chofer (hora de llegada,
        novedades del viaje, quién la registró). Debajo:
        · si `confirmadaAt === null` → formulario "Confirmar recepción"
          (recibidoPor + novedades de recepción) que hace `PATCH`.
        · si `confirmadaAt !== null` → los datos de recepción en solo lectura,
          con quién confirmó y cuándo.

D2. TRAMPA DEL `datetime-local`. Para la fecha usa `<Input type="datetime-local">`
    con `max` puesto en el momento actual (refuerza A1 del lado del cliente).

    El valor que devuelve ese input es hora LOCAL sin zona ("2026-08-21T15:30").
    La conversión correcta es `new Date(value).toISOString()` — JS lo interpreta
    como hora local del navegador y produce el UTC correcto.
    NO le concatenes "Z" al string ni uses `.slice()` para armar el ISO a mano:
    eso manda la hora local etiquetada como UTC y el acta queda corrida las
    horas del huso (en Venezuela, 4 horas). Es un error clásico y silencioso:
    la fecha se ve "casi bien" y nadie lo nota hasta que descuadra un reporte.

D3. Los campos de texto vacíos se mandan como `null`, no como "".

D4. Al guardar (POST o PATCH), invalidar siguiendo el patrón de cache-bust que
    ya usa este archivo para el peso estimado: `getGetTrasladoQueryKey(id)` y
    `getListTrasladosQueryKey()`. La lista tiene que refrescar porque
    `recepcionSinValidar` puede cambiar.

D5. Nombres de los hooks generados: `useRegisterDispatchActa`,
    `useConfirmDispatchActa`, `useGetDispatchActa` /
    `getGetDispatchActaQueryKey`. No hace falta llamar a `useGetDispatchActa`
    en esta pantalla — el acta ya viene embebida en `TrasladoDetail`.
