════════ CONTEXTO DEL PROYECTO ════════

LogiFleet es un sistema de gestión logística de flota. Importa ventas y
traslados internos desde Odoo, planifica despachos (vehículo + chofer + ruta),
calcula costos, y tiene una app móvil para choferes.

Monorepo pnpm workspaces, Node 24, TypeScript 5.9. Estructura:

  lib/db/               Drizzle: schema (fuente de verdad) + migraciones embebidas
  lib/api-spec/         openapi.yaml — contrato de la API + config de Orval
  lib/api-zod/          GENERADO — NO editar
  lib/api-client-react/ GENERADO (hooks React Query) — NO editar
  artifacts/api-server/ API Express 5
  artifacts/logistics/  Web React + Vite + wouter + shadcn/ui
  artifacts/chofer/     App móvil Expo
  e2e/                  Vitest (API) + Playwright (UI)

Lee `replit.md` y `.agents/memory/`. CRÍTICOS para esta tarea:

1. DESPACHOS POLIMÓRFICOS (schema + migración)

   Hoy `dispatches.ventaId` es NOT NULL: todo despacho existe porque hay una
   venta. Un traslado no tiene venta.

   En lib/db/src/schema/dispatches.ts:
     - `ventaId` pasa a NULLABLE
     - nueva columna `tipo` text NOT NULL DEFAULT 'venta'  -- 'venta' | 'traslado'
     - nueva columna `trasladoId` integer NULL REFERENCES traslados(id)

   Migración `lib/db/src/migrations/0010_dispatches_polimorficos.ts`,
   idempotente, registrada en su index.ts:
     - ALTER COLUMN venta_id DROP NOT NULL
     - ADD COLUMN IF NOT EXISTS tipo / traslado_id (+ FK con guarda)
     - UPDATE dispatches SET tipo='venta' WHERE tipo IS NULL, y recién
       después el SET NOT NULL (mismo patrón que usó 0008 con deliveries.tipo)
     - CHECK constraint con guarda: exactamente uno de venta_id / traslado_id
       poblado, y coherente con tipo:
         (tipo='venta'    AND venta_id IS NOT NULL AND traslado_id IS NULL)
      OR (tipo='traslado' AND traslado_id IS NOT NULL AND venta_id IS NULL)
     - índice en traslado_id

2. AUDITAR TODA LECTURA DE dispatches.ventaId

   Volver ventaId nullable rompe el tipado en varios sitios. Corre este grep y
   revisa CADA resultado:

     grep -rn "dispatchesTable.ventaId\|dispatch\.ventaId\|d\.ventaId" \
       --include=*.ts artifacts/api-server/src

   Los que ya identifiqué y qué hacer con cada uno:

   a) services/saleEstadoSync.ts línea ~59 — `reconcileSaleEstados()` hace
      `byVenta.set(d.ventaId, list)`. Con ventaId null, `null` se volvería una
      clave del Map y corrompería la reconciliación.
      → Agregar `eq(dispatchesTable.tipo, "venta")` al WHERE de esa consulta.
      Filtrar por `tipo`, no por `ventaId is not null`: dice POR QUÉ se excluyen.

   b) routes/dispatches.ts línea ~115 y ~138 — `buildDispatchRow` y
      `buildDispatchDetail` hacen `eq(salesTable.id, d.ventaId)`.
      → Cuando tipo='traslado', no buscar venta: resolver los datos de la carga
      desde `traslados` + `deliveries` (referencia, origen, destino) en su lugar.

   c) routes/dispatches.ts POST /dispatches (línea ~162) — hoy exige que la
      venta exista y compara capacidad contra sale.pesoTotal/volumenTotal.
      → Aceptar también `{ tipo: 'traslado', trasladoId }`. Validar que el
      traslado existe. La comparación de capacidad usa el PESO EFECTIVO del
      traslado (ver punto 4), no los totales de la venta.
      → Mantener intacta la regla actual: null = sin dato NO bloquea el
      despacho (no se puede comparar lo que no se conoce).

   d) routes/dispatches.ts POST y routes/driver.ts línea ~175 — llaman
      `syncSaleEstadoFromDispatch(dispatch.ventaId)`.
      → Llamarla SOLO cuando tipo='venta'. Un traslado nunca debe tocar
      sales.estado.

   e) services/deliverySync.ts líneas ~285-298 — construye dispatchBySaleId.
      → Agregar el filtro `tipo='venta'` por la misma razón que (a).

4. CONCEPTO "PESO EFECTIVO" EN EL CONTRATO

   Agregar a TrasladoSummary y TrasladoDetail dos campos derivados:

     pesoEfectivoKg   number | null   -- pesoCalculadoKg ?? pesoEstimadoKg
     origenPeso       "odoo" | "estimado" | null

   Reglas:
     - Si pesoCalculadoKg tiene valor → pesoEfectivoKg = ese, origenPeso='odoo'
     - Si no, y pesoEstimadoKg tiene valor → origenPeso='estimado'
     - Si ninguno → ambos null
   El dato de Odoo SIEMPRE gana sobre la estimación. Nunca se mezclan ni se
   suman.

   Exponer también `pesoEstimadoKg` crudo en el detalle (para poder editarlo).

   ⚠ NO toques lib/fleet.ts ni ningún helper compartido de medidas. Lee
   .agents/memory/measurement-domain-semantics.md: ventas tratan los totales
   no positivos como ausencia por seguridad de capacidad, traslados reservan
   null. Cambiar el helper compartido rompería Ventas, Pre-Despacho y los
   wizards en silencio. La lógica de peso efectivo vive en el dominio de
   traslados.
