════════ CONTEXTO DEL PROYECTO ════════

LogiFleet es un sistema de gestión logística de flota. Importa ventas desde Odoo,
planifica despachos (vehículo + chofer + ruta), calcula costos de peajes y
combustible, y tiene una app móvil para choferes.

Monorepo pnpm workspaces, Node 24, TypeScript 5.9. Estructura:

  lib/db/               Drizzle: schema (fuente de verdad) + migraciones embebidas
  lib/api-spec/         openapi.yaml — contrato de la API + config de Orval
  lib/api-zod/          GENERADO desde el spec — NO editar
  lib/api-client-react/ GENERADO desde el spec (hooks React Query) — NO editar
  artifacts/api-server/ API Express 5 (routers en src/routes/, servicios en src/services/)
  artifacts/logistics/  Web React + Vite
  artifacts/chofer/     App móvil Expo
  e2e/                  Vitest (API) + Playwright (UI)

Lee `replit.md` en la raíz y `.agents/memory/`. Para esta tarea son relevantes:
  - .agents/memory/db-migrations-boot.md
  - .agents/memory/sales-totales-null.md          (null vs 0 — regla central)
  - .agents/memory/odoo-stock-picking.md
  - .agents/memory/api-server-restart-after-codegen.md
  - .agents/memory/task-db-schema-drift.md

1. GENERALIZAR `deliveries` A "MOVIMIENTO DE ALMACÉN"

   Hoy la tabla espeja solo albaranes de venta. Pasa a espejar también traslados:

2. NUEVA TABLA `traslados`

   Es la entidad de PLANIFICACIÓN de LogiFleet, deliberadamente separada del
   espejo de Odoo:
   - id serial PK
   - deliveryId integer UNIQUE REFERENCES deliveries(id) ON DELETE SET NULL
   - odooPickingId integer UNIQUE                 -- NULLABLE a propósito
   - almacenOrigenId integer REFERENCES almacenes(id)
   - almacenDestinoId integer REFERENCES almacenes(id)
   - estadoLogistico text NOT NULL DEFAULT 'por_planificar'
   - pesoCalculadoKg real
   - volumenCalculadoM3 real
   - pesoEstimadoKg real
   - notas text
   - createdAt timestamptz NOT NULL DEFAULT now()

   POR QUÉ ON DELETE SET NULL: si un picking desaparece de Odoo, el traslado y su
   futuro despacho deben sobrevivir — el camión sí hizo el viaje. Nunca borrar en
   cascada hacia arriba.
   POR QUÉ odooPickingId nullable: permite, más adelante, traslados creados en
   LogiFleet antes de existir en Odoo.

   estadoLogistico admite: por_planificar | planificado | en_carga | en_transito |
                           entregado | confirmado_odoo | cancelado
   En esta tarea solo se define la columna; la lógica que la mueve va en la
   tarea siguiente.

   Backfill en la misma migración: UPDATE deliveries SET tipo='venta' donde sea

4. PESO Y VOLUMEN DE PRODUCTOS DESDE ODOO

   - nuevas columnas `products.pesoKgOdoo` real y `products.volumenM3Odoo` real
     (nullable), en la misma migración 0008
   - en artifacts/api-server/src/services/productSync.ts, mapear los campos
     `weight` y `volume` de Odoo hacia esas columnas

   TRAMPA CRÍTICA: en Odoo esos campos son float con default 0.0, NO false. Un
   producto sin peso cargado llega como 0. Mapear SIEMPRE `<= 0 → null`. Un 0 se
   leería como dato real y arruinaría la recomendación de vehículo (5.000
   conectores "pesando cero kilos" recomendarían una moto).

   NO reutilices las columnas de dimensiones dormidas (products.peso_kg,
   largo_cm, ancho_cm, alto_cm, apilable, fragil, dimensiones_confirmadas).
   Tienen datos viejos de la medición manual eliminada en ago 2026 y
   contaminarían el dato nuevo. Columnas nuevas.
